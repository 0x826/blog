    浏览器&网络 · 面试 · 前端

    模块一：浏览器原理与渲染机制

    1. 浏览器是多进程多线程架构吗？请描述现代浏览器（以 Chrome 为例）的进程模型

    是的，现代浏览器是多进程且多线程的架构。

    • 浏览器主进程 (Browser Process)：负责界面显示（地址栏、书签）、前后进后退、网络请求、文件访问等。包含 UI 线程、网络线程、存储线程等。
    • 渲染进程 (Renderer Process)：每个 Tab 页通常对应一个独立的渲染进程（保证隔离性，一个 Tab 崩溃不影响其他）。负责 HTML/CSS 解析、JS 执行、页面渲染。包含 GUI 渲染线程、JS 引擎线程、事件触发线程、定时器线程等。
    • GPU 进程 (GPU Process)：负责 3D 绘制、CSS 动画合成、硬件加速。
    • 网络进程 (Network Process)：负责所有的网络请求（Chrome 后期从主进程剥离出来）。
    • 插件/扩展进程：独立运行，防止插件崩溃影响浏览器。

    2. 从输入 URL 到页面展示，完整发生了什么？

    1. URL 解析与判断：判断是搜索还是 URL，补全协议（如 http://）。
    2. 查找缓存：依次查找浏览器缓存 -> 操作系统缓存 -> 路由器缓存 -> ISP DNS 缓存。
    3. DNS 解析：若缓存未命中，向 DNS 服务器发起查询，获取 IP 地址。
    4. TCP 连接：与服务器进行 TCP 三次握手（若是 HTTPS 还需进行 TLS 握手）。
    5. 发送 HTTP 请求：构建请求报文（请求行、请求头、请求体），发送给服务器。
    6. 服务器处理与响应：服务器处理请求，返回 HTTP 响应报文（状态码、响应头、HTML 内容）。
    7. 浏览器解析与渲染：
      • 解析 HTML 构建 DOM 树。
      • 解析 CSS 构建 CSSOM 树。
      • 合并生成 渲染树 (Render Tree)。
      • 布局 (Layout)：计算节点几何信息（位置、大小）。
      • 绘制 (Paint)：绘制像素。
      • 合成 (Composite)：将图层合成为屏幕上的最终图像（GPU 加速）。
    8. JS 执行：遇到 <script> 标签时，暂停 DOM 构建，下载并执行 JS（可能修改 DOM/CSSOM）。
    9. TCP 四次挥手：请求完成且连接空闲后，断开 TCP 连接（若是 Keep-Alive 则保持连接）。

    3. DNS 解析的完整过程与优化手段

    • 过程：浏览器缓存 -> OS 缓存 (hosts 文件) -> 本地 DNS 服务器（递归查询） -> 根域名服务器 -> 顶级域名服务器（如 .com） -> 权威域名服务器（返回最终 IP）。
    • 优化手段：
      • DNS 预解析：<link rel="dns-prefetch" href="//example.com">。
      • HTTPDNS：使用 HTTP 协议直接向阿里云/腾讯云等 DNS 服务器请求解析，绕过运营商 LocalDNS，防劫持、防缓存不生效。
      • DNS-over-HTTPS (DoH)：加密 DNS 请求，防窃听和劫持。

    4. 浏览器的渲染流程（关键渲染路径）

    关键渲染路径 (Critical Rendering Path) 是指从接收 HTML/CSS/JS 到像素渲染到屏幕上的全过程。

    1. 构建 DOM：解析 HTML，遇到标签创建节点，遇到 <script> 阻塞解析。
    2. 构建 CSSOM：解析 CSS，构建样式规则树。
    3. 构建 Render Tree：将 DOM 和 CSSOM 结合，忽略不可见元素（如 display: none，但 visibility: hidden 会保留）。
    4. Layout (回流)：计算 Render Tree 中每个节点的精确位置和大小。
    5. Paint (重绘)：根据 Layout 结果，绘制节点的背景、颜色、边框、阴影等像素。
    6. Composite (合成)：将节点分层，由 GPU 将图层合成为最终页面。

    5. 重排（Reflow）和重绘（Repaint）的区别？触发与优化

    • 重排 (Reflow/Layout)：元素的尺寸、位置发生变化，浏览器需要重新计算 Render Tree。必定触发重绘。
    • 重绘 (Repaint)：元素外观（如颜色、背景）变化，但尺寸位置不变。浏览器重新绘制像素。不一定触发重排。
    • 触发重排：添加/删除可见 DOM、改变元素位置/尺寸、读取 offsetHeight/Width、窗口 resize。
    • 触发重绘：改变 color、background-color、visibility。
    • 优化：批量修改 DOM（使用 DocumentFragment 或 cssText）、避免频繁读取布局信息、将复杂动画元素设置为绝对定位或固定定位（脱离文档流）。

    6. 什么是布局抖动（Layout Thrashing）？怎么解决？

    • 本质：在 JS 中交替进行“修改 DOM 样式”和“读取 DOM 布局信息（如 offsetTop）”。这会导致浏览器被迫中断渲染流水线，进行强制同步布局（Forced Synchronous Layout），极大消耗性能。
    • 解决：读写分离。先批量读取所有布局信息并缓存到变量中，然后再批量修改 DOM 样式。

    7. 什么是合成层（Compositing Layer）？GPU 加速是怎么回事？

    • 合成层：浏览器在渲染时，会将页面拆分成多个图层（Layer）。某些特定的 CSS 属性（如 transform, opacity, filter）或特定元素（如 <video>, <iframe>, 设置了 will-change 的元素）会被提升为独立的合成层。
    • GPU 加速原理：独立的合成层会交由 GPU 进行合成（Composite）。当这些元素的 transform 或 opacity 改变时，不需要经过 Layout 和 Paint 阶段，直接在 GPU 中进行图层变换，性能极高。

    8. script 标签的 defer 和 async 有什么区别？

    • 无属性：阻塞 DOM 解析，下载并立即执行。
    • async (异步)：下载不阻塞 DOM 解析，下载完成后立即执行（会阻塞 DOM 解析），执行顺序不保证。适合独立脚本（如统计代码）。
    • defer (延迟)：下载不阻塞 DOM 解析，延迟到 DOM 解析完成后（DOMContentLoaded 之前）按顺序执行。适合有依赖关系的业务脚本。

    9. DOMContentLoaded 和 load 事件的区别？

    • DOMContentLoaded：HTML 文档被完全加载和解析完成，DOM 树构建完毕，无需等待样式表、图片、iframe 等子资源加载。
    • load：页面所有资源（包括图片、CSS、iframe 等）全部加载完毕。触发时间晚于前者。

    10. 事件的冒泡和捕获机制是什么？事件委托如何实现？

    • 机制：W3C 规定事件流分为三阶段：捕获阶段（从 window 到目标元素） -> 目标阶段 -> 冒泡阶段（从目标元素到 window）。
    • 事件委托：利用事件冒泡机制，将子元素的事件监听器绑定在父元素上。通过 event.target 判断实际触发事件的子元素。
    • 优势：减少内存消耗（减少监听器数量）；动态添加的子元素自动拥有事件处理能力。

    11. 浏览器的事件循环（Event Loop）和 Node 的有什么不同？

    • 浏览器：
      • 执行同步代码（宏任务）。
      • 清空微任务队列（Promise.then, MutationObserver）。
      • 尝试渲染 UI（RequestAnimationFrame）。
      • 执行下一个宏任务（setTimeout, setInterval, I/O, UI rendering）。
    • Node.js：基于 libuv，分为 6 个阶段（timers -> pending callbacks -> idle/prepare -> poll -> check -> close callbacks）。微任务在每个阶段切换时执行，而不是像浏览器那样在宏任务执行完后执行。

    12. requestAnimationFrame 和 requestIdleCallback 的作用与区别？

    • rAF：在浏览器下一次重绘之前执行回调，频率与屏幕刷新率同步（通常 60Hz/16.6ms）。用于平滑动画。
    • rIC：在浏览器空闲时间执行回调。用于执行低优先级任务（如非关键日志上报、长列表预计算），不阻塞用户交互和动画。
    • 对比 setTimeout：setTimeout 只是将任务加入宏任务队列，不关心浏览器渲染状态，可能导致掉帧；rAF 与渲染管线绑定，性能更好。

    13. 浏览器渲染与 JS 执行的时机关系？为什么“先 Promise 后渲染”？

    • 关系：JS 是单线程的，且可以修改 DOM。如果 JS 执行和渲染并行，会导致渲染状态不一致。因此，JS 执行会阻塞渲染。
    • 先 Promise 后渲染：Promise 的回调属于微任务。浏览器在每次执行完一个宏任务（或同步代码）后，会先清空所有微任务，然后再进行 UI 渲染。这保证了 JS 对 DOM 的多次修改能在渲染前合并，避免中间状态被用户看到。

    模块二：缓存机制

    14. 浏览器缓存的整体机制？强缓存和协商缓存的区别？

    • 强缓存：不发请求，直接使用本地缓存。通过 Cache-Control (max-age) 或 Expires 控制。命中时状态码为 200 (from memory/disk cache)。
    • 协商缓存：强缓存失效后，向服务器发请求，带上缓存标识（If-None-Match 或 If-Modified-Since）。服务器对比后，若未修改返回 304 Not Modified（使用本地缓存）；若修改了返回 200 及新资源。

    15. Cache-Control 常用指令？

    • max-age=<seconds>：缓存最大有效时间（相对时间）。
    • no-cache：不使用强缓存，每次都要走协商缓存。
    • no-store：绝对不缓存，每次都要重新下载。
    • immutable：在 max-age 内，内容绝对不变，连协商缓存都不走（常用于带 Hash 的静态资源）。

    16. ETag 和 Last-Modified 的优缺点？为什么有了后者还要 ETag？

    • Last-Modified：文件最后修改时间。缺点：精度只到秒；文件内容没变但修改时间变了（如 touch 命令），会导致缓存失效。
    • ETag：文件内容的哈希值（如 inode + 修改时间 + 大小，或内容 hash）。优点：更精确，只要内容不变，ETag 就不变。优先级高于 Last-Modified。

    17. memory cache 和 disk cache 的区别？

    • memory cache：内存缓存。速度极快，但容量小，Tab 页关闭即清除。通常缓存小体积、刚加载过的资源。
    • disk cache：磁盘缓存。速度较慢，容量大，持久化存储。通常缓存大文件或跨 Tab 共享的资源。
    • 选择：浏览器优先查找 memory cache，未命中再找 disk cache。

    18. Service Worker 与 PWA

    • Service Worker：运行在浏览器背后的独立线程，可以拦截和处理网络请求，管理缓存（Cache API），支持推送通知。
    • PWA (Progressive Web App)：一种 Web 技术集合，旨在提供类似原生 App 的体验。核心技术包括：Service Worker（离线缓存）、Web App Manifest（添加到主屏幕）、Push API。

    19. 用户刷新页面对缓存的影响？

    • 地址栏回车 / 点击链接：正常走缓存（强缓存 -> 协商缓存）。
    • F5 / 点击刷新按钮：跳过强缓存，直接走协商缓存（带上 Cache-Control: max-age=0）。
    • Ctrl + F5 / 强制刷新：跳过所有缓存（强缓存和协商缓存都跳过），请求头带上 Cache-Control: no-cache 和 Pragma: no-cache。

    模块三：本地存储

    20. Cookie、localStorage、sessionStorage、IndexedDB 的区别？

    特性 Cookie localStorage sessionStorage IndexedDB
    容量 4KB 5MB - 10MB 5MB - 10MB 极大 (通常 > 50MB)
    生命周期 设定的过期时间 永久（需手动清除） 会话级（关闭 Tab 即清） 永久（需手动清除）
    服务端通信 每次请求自动携带 不参与 不参与 不参与
    API 需手动解析字符串 简单的 key-value 简单的 key-value 异步 API，支持索引/事务

    21. Cookie 的重要属性及作用？

    • Domain / Path：限制 Cookie 的发送范围（域名和路径）。
    • Expires / Max-Age：设置过期时间。
    • Secure：仅在使用 HTTPS 时发送。
    • HttpOnly：禁止 JS 通过 document.cookie 访问，有效防御 XSS 攻击窃取 Cookie。
    • SameSite：限制跨站请求携带 Cookie（Strict, Lax, None），防御 CSRF。

    22. localStorage 存 Token 安全吗？和 Cookie 怎么选？

    • 不安全：localStorage 无法设置 HttpOnly，一旦发生 XSS 攻击，Token 会被直接窃取。
    • 选择：
      • 推荐方案：将 Access Token 存入 HttpOnly Cookie（防 XSS），结合 SameSite 和 CSRF Token（防 CSRF）。
      • 折中方案：若必须用 localStorage（如跨域场景），需严格防范 XSS，并使用短效 Access Token + 长效 Refresh Token。

    模块四：跨域与安全

    23. 什么是同源策略？限制了什么？

    • 同源：协议、域名、端口完全一致。
    • 限制：1) 无法读取跨域的 Cookie/LocalStorage；2) 无法操作跨域的 DOM；3) 无法发送跨域的 XHR/Fetch 请求（受 CORS 限制）。

    24. CORS 跨域原理？简单请求和预检请求？

    • 原理：浏览器在请求头中加入 Origin，服务器通过响应头 Access-Control-Allow-Origin 决定是否允许。
    • 简单请求：方法为 GET/POST/HEAD，且 Content-Type 仅限 text/plain, multipart/form-data, application/x-www-form-urlencoded。直接发送请求。
    • 预检请求 (Preflight)：非简单请求（如 PUT/DELETE，或 Content-Type 为 application/json）。浏览器会先发送一个 OPTIONS 请求，询问服务器是否允许（检查 Access-Control-Allow-Methods/Headers），允许后再发送真实请求。

    25. 其他跨域解决方案？

    • JSONP：利用 <script> 标签不受同源策略限制，仅支持 GET。
    • postMessage：用于 iframe、Web Worker、跨 Tab 通信。
    • Nginx 反向代理：最常用，前端请求同源 Nginx，Nginx 转发到目标服务器（彻底绕过浏览器限制）。
    • WebSocket：WS 协议不受同源策略限制。

    26. CSRF 攻击原理与防御？

    • 原理：攻击者诱导用户访问恶意网站，该网站自动向目标网站发起请求。由于浏览器会自动携带目标网站的 Cookie，导致请求被目标网站认为是合法用户发起的。
    • 防御：1) 设置 Cookie 的 SameSite 属性；2) 验证 Origin / Referer 请求头；3) 在表单或请求头中加入随机生成的 CSRF Token 并校验。

    27. 点击劫持与 CSP？

    • 点击劫持：攻击者用透明的 <iframe> 将目标网站覆盖在诱导页面上，用户以为点击的是诱导页按钮，实际点击了 iframe 里的目标网站按钮。
    • 防御：设置响应头 X-Frame-Options: DENY/SAMEORIGIN，或 CSP 的 frame-ancestors 指令。
    • CSP (内容安全策略)：通过白名单机制，严格限制浏览器可以加载和执行的外部资源（JS/CSS/图片），是防御 XSS 的终极手段。

    28. 中间人攻击 (MITM) 与 SQL 注入？

    • MITM：攻击者在客户端和服务器之间拦截、篡改通信。防御：使用 HTTPS，并严格校验数字证书。
    • SQL 注入：后端未对用户输入进行过滤，导致恶意 SQL 被执行。前端职责：前端无法彻底防御，但需做输入校验和特殊字符转义，减轻后端压力，配合后端使用参数化查询。

    模块五：网络与 HTTP

    29. HTTP 报文结构与常见状态码/方法

    • 结构：起始行（请求行/状态行）、请求头/响应头、空行、请求体/响应体。
    • 状态码：200 OK, 301 永久重定向, 302 临时重定向, 304 协商缓存命中, 400 坏请求, 401 未授权, 403 禁止, 404 未找到, 500 服务器内部错误, 502 网关错误, 504 网关超时。
    • 幂等性：执行一次和执行多次结果相同。GET、PUT、DELETE 是幂等的；POST 不是。

    30. HTTP 版本演进 (1.0 -> 1.1 -> 2 -> 3)

    • 1.0：短连接，每次请求都要 TCP 握手。
    • 1.1：长连接（Connection: keep-alive），管线化（仍有队头阻塞）。
    • 2.0：二进制分帧、多路复用（解决 HTTP 层队头阻塞）、头部压缩 (HPACK)、服务器推送。
    • 3.0：基于 UDP (QUIC 协议)，彻底解决 TCP 层队头阻塞，0-RTT 建连，连接迁移。

    31. HTTP/2 的多路复用与队头阻塞？

    • 多路复用：HTTP/2 将请求和响应拆分为多个二进制帧，在同一个 TCP 连接上交替、并行传输，解决了 HTTP 1.1 中“同一时间只能处理一个请求”的队头阻塞。
    • 为什么仍有队头阻塞：HTTP/2 解决了应用层的队头阻塞，但底层仍依赖 TCP 协议。TCP 是可靠传输，如果某个 TCP 包丢失，整个 TCP 连接都会阻塞等待重传，导致其上所有的 HTTP/2 流都被阻塞（TCP 层队头阻塞）。这就是 HTTP/3 引入 QUIC (UDP) 的原因。

    32. HTTPS 与 TLS 握手过程？对称与非对称加密？

    • 区别：HTTP 明文传输，HTTPS = HTTP + TLS/SSL（加密传输）。
    • 加密方式：
      • 对称加密（如 AES）：加密解密用同一把密钥。速度快，但密钥分发不安全。
      • 非对称加密（如 RSA）：公钥加密，私钥解密。安全性高，但速度慢。
      • HTTPS 结合：使用非对称加密安全地协商出“会话密钥”，后续通信使用对称加密（兼顾安全与性能）。
    • TLS 握手：ClientHello (支持加密算法) -> ServerHello (确定算法) + 证书 -> 客户端验证证书 -> 客户端生成随机数，用服务器公钥加密发送 -> 服务器用私钥解密得到随机数 -> 双方用该随机数生成对称会话密钥 -> 开始加密通信。

    33. TCP 三次握手与四次挥手？

    • 三次握手：Client SYN -> Server SYN+ACK -> Client ACK。为什么3次：防止已失效的连接请求报文段突然又传送到了服务端，产生错误连接（浪费资源）。
    • 四次挥手：Client FIN -> Server ACK -> Server FIN -> Client ACK。为什么4次：TCP 是全双工的，Server 收到 FIN 时可能还有数据要发，所以先回 ACK，等数据发完再发 FIN。
    • TIME_WAIT (2MSL)：Client 收到 Server 的 FIN 后进入。作用：1) 确保最后一个 ACK 能到达 Server（若丢失可重传）；2) 等待网络中该连接的残留报文消失，防止新连接收到旧数据。

    34. TCP 可靠传输、流量控制与拥塞控制？

    • 可靠传输：通过序列号、确认应答 (ACK)、超时重传、滑动窗口保证数据不丢、不乱序。
    • 流量控制：端到端。接收方通过滑动窗口告诉发送方自己的接收能力，防止发送方发得太快撑爆接收方缓冲区。
    • 拥塞控制：网络端。发送方探测网络拥堵情况（慢开始、拥塞避免、快重传、快恢复），防止发得太快导致路由器丢包。

    35. WebSocket 与 SSE？

    • WebSocket：全双工通信，独立协议（通过 HTTP 升级），开销小，适合高频双向交互（如聊天、游戏）。需自己做心跳保活。
    • SSE (Server-Sent Events)：服务端单向推送，基于 HTTP 协议，自带断线重连，适合单向通知（如股票行情、日志流）。

    36. CDN 原理与前端利用？

    • 原理：内容分发网络。通过智能调度系统，将用户请求路由到距离最近、负载最轻的边缘节点，从缓存中获取资源。
    • 前端利用：静态资源（JS/CSS/图片）全部上 CDN；动态 API 请求走源站（或配置动态路由回源）。

    模块六：性能优化

    37. Core Web Vitals 核心指标？

    • LCP (Largest Contentful Paint)：最大内容绘制，衡量加载性能。应 < 2.5s。
    • INP (Interaction to Next Paint)：交互到下一帧绘制，衡量交互响应性（替代了 FID）。应 < 200ms。
    • CLS (Cumulative Layout Shift)：累积布局偏移，衡量视觉稳定性。应 < 0.1。

    38. 如何优化 LCP / CLS / INP？

    • 优化 LCP：优化关键资源（图片 WebP/AVIF、预加载 <link rel="preload">）、减少关键渲染路径、使用 CDN、SSR/SSG。
    • 优化 CLS：为图片/视频设置明确的 width/height；为广告/嵌入内容预留空间；避免在现有内容上方动态插入 DOM（使用 transform 代替 top/left 动画）。
    • 优化 INP：拆分长任务（Long Tasks < 50ms）；使用 requestIdleCallback 或 Web Worker 处理非关键计算；优化事件监听器（防抖/节流）。

    39. 前端性能优化大方向归纳？

    1. 网络层：DNS 预解析、HTTP/2、CDN、减少请求数、减小资源体积（Gzip/Brotli）。
    2. 资源层：代码分割、懒加载、图片/字体优化、缓存策略。
    3. 渲染层：避免重排重绘、GPU 加速、虚拟列表、Web Worker。
    4. 架构层：SSR/SSG、骨架屏、微前端按需加载。

    40. 图片与字体优化手段？

    • 图片：使用 WebP/AVIF；响应式图片 (srcset)；懒加载 (loading="lazy")；小图标使用 SVG 或 IconFont；雪碧图（HTTP/1.1 下）。
    • 字体：字体子集化（Fontmin，只保留用到的字符）；使用 font-display: swap 防止 FOIT（字体加载时文本不可见）；优先使用系统默认字体。

    41. 内存泄漏排查与 Performance API？

    • 排查：Chrome DevTools -> Memory 面板 -> 拍摄 Heap Snapshot。对比操作前后的快照，查找 “Detached DOM tree”（分离的 DOM）或被闭包意外引用的大对象。
    • 常见原因：未清理的 setInterval/addEventListener；闭包引用；全局变量；脱离 DOM 树的引用。
    • Performance API：使用 PerformanceObserver 监听 largest-contentful-paint、layout-shift 等条目，精准采集 Web Vitals 数据。

    42. 防抖 (debounce) 和节流 (throttle)？

    • 防抖：事件触发后 n 秒才执行，若 n 秒内再次触发，重新计时。场景：搜索框输入、窗口 resize 后计算。
    • 节流：事件触发后，保证 n 秒内只执行一次。场景：滚动加载、鼠标连续点击、高频拖拽。

    43. CSR、SSR、SSG、同构的区别与选型？

    • CSR (客户端渲染)：首屏慢，SEO 差。适合后台管理系统、强交互应用。
    • SSR (服务端渲染)：首屏快，SEO 好，服务器压力大。适合 C 端首屏要求高、SEO 要求高的页面（如电商首页）。
    • SSG (静态站点生成)：构建时生成 HTML，速度最快。适合博客、文档、官网。
    • 同构：一套 React/Vue 代码，既能在服务端渲染出 HTML，又能在客户端接管（Hydration）实现交互。

    44. 资源预加载 link rel 的区别？

    • preload：当前页面必需的关键资源，高优先级立即加载。
    • prefetch：未来导航可能需要的资源，低优先级，在浏览器空闲时加载。
    • preconnect：提前与第三方域名建立 TCP/TLS 连接。
    • dns-prefetch：提前进行 DNS 解析。

    45. 减少 HTTP 请求与 HTTP/2 的变化？

    • HTTP/1.1 时代：合并 JS/CSS 文件、雪碧图、内联小图片（Base64）。
    • HTTP/2 时代：由于多路复用，不再需要合并文件。反而应该拆分文件（按需加载），避免单个大文件阻塞，且能更好地利用浏览器缓存。

    模块七：补充遗漏的高频/深度核心考点（2024-2026 必备）

    46. V8 引擎的垃圾回收机制 (GC) 是怎样的？

    • 分代回收：V8 将内存分为新生代（存活时间短的小对象，如临时变量）和老生代（存活时间长的大对象，如全局配置）。
    • 新生代 (Scavenge 算法)：分为 From 和 To 两个空间。对象先在 From 分配，GC 时将存活对象复制到 To，然后清空 From，两者角色互换。效率高，但浪费一半内存。
    • 老生代 (Mark-Sweep & Mark-Compact)：
      • 标记清除：遍历所有对象，标记存活对象，清除未标记对象。会产生内存碎片。
      • 标记整理：在清除后，将存活对象向一端移动，清理边界外的内存。解决碎片问题，但耗时。

    47. 跨域 Cookie 丢失问题与 SameSite 深度解析

    • 痛点：前端跨域请求（如 a.com 请求 api.b.com），即使设置了 withCredentials: true，Cookie 也可能带不上。
    • 原因与解决：
      1. 后端 Cookie 必须设置 SameSite=None 且 Secure=true。
      2. 前端请求必须设置 credentials: 'include' (Fetch) 或 withCredentials: true (XHR)。
      3. 注意：Chrome 80+ 默认将 SameSite 设为 Lax，且正在逐步淘汰第三方 Cookie。现代架构更推荐将前端和 API 部署在同主域下（如 web.app.com 和 api.app.com），通过设置 Domain=.app.com 来共享 Cookie，彻底避开跨域 Cookie 限制。

    48. Brotli (br) 压缩与 Gzip 的区别？

    • Brotli：Google 推出的压缩算法。相比 Gzip，在相同压缩率下速度更快，在相同速度下压缩率更高（通常比 Gzip 小 15%-20%）。
    • 前端应用：Nginx 开启 brotli 模块；构建工具（如 Webpack/Vite）使用 compression-webpack-plugin 预生成 .br 文件，配合 Nginx 的 gzip_static / brotli_static 直接返回，避免服务器实时压缩消耗 CPU。

    49. Service Worker 的生命周期与更新机制（易踩坑点）

    • 生命周期：register -> install (可 skipWaiting) -> waiting -> activate (可 clients.claim) -> activated -> redundant。
    • 更新机制：浏览器会对比 SW 文件的字节（哪怕只改了一个空格）。新 SW 安装后，会进入 waiting 状态，必须等旧 SW 控制的页面全部关闭，新 SW 才会 activate。
    • 强制更新：开发时勾选 DevTools 的 “Update on reload”，或在代码中调用 registration.update()，并在 install 中调用 self.skipWaiting()，在 activate 中调用 self.clients.claim() 实现立即接管。

    50. 前端工程化中的 Tree-shaking 原理？

    • 原理：基于 ES6 Module 的静态结构特性（import/export 在编译时确定，不能动态引入）。
    • 过程：Webpack/Rollup 在打包时，通过 AST 分析，标记出所有未被使用的 export 变量（标记为 /* unused harmony export */），然后在代码压缩阶段（Terser）将这些死代码剔除。
    • 注意：必须使用 ESM 语法；避免在 import 时引入带有副作用的模块（若有，需在 package.json 中配置 sideEffects 字段声明）。
