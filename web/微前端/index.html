    微前端

    微前端 是一种类似于微服务的架构，单页面前端应用由单一应用转变为多个小型前端应用聚合为一的应用。各个前端独立开发，独立部署。

    qiankun

    qiankun 方案是基于 single-spa 的 微前端 方案。

    特点

    • html entry 的方式引入子应用，相比 js entry 极大的降低了应用改造的成本；
    • 完备的沙箱方案，js 沙箱做了 SnapshotSandbox、LegacySandbox、ProxySandbox 三套渐进增强方案，css 沙箱做了 strictStyleIsolation、experimentalStyleIsolation 两套适用不同场景的方案；
    • 做了静态资源预加载能力；

    不足

    • 接入与治理成本仍然较高：工程化、生命周期、静态资源路径、路由隔离、通信规范都需要额外设计；
    • 沙箱隔离在复杂场景下仍可能带来兼容性或性能开销（如 Shadow DOM 样式隔离、全局对象代理）；
    • 多子应用并行挂载虽可通过配置实现，但在状态管理、样式隔离、资源竞争等方面复杂度明显上升；
    • 对 Vite/原生 ESM 的支持并非“开箱即用”，通常需要插件或额外改造，特定场景仍可能遇到兼容问题；
    • 框架层不内建统一的“跨应用保活”能力，通常需在子应用或业务层自行实现缓存与恢复策略。

    micro-app 方案

    micro-app 是基于 webcomponent + qiankun sandbox 的微前端方案。

    特点

    使用 webcomponet 加载子应用相比 single-spa 这种注册监听方案更加优雅； 复用经过大量项目验证过 qiankun 的沙箱机制也使得框架更加可靠； 组件式的 api 更加符合使用习惯，支持子应用保活； 降低子应用改造的成本，提供静态资源预加载能力； 不足

    接入成本较 qiankun 有所降低，但是路由依然存在依赖； 多应用激活后无法保持各子应用的路由状态，刷新后全部丢失； css 沙箱依然无法绝对的隔离，js 沙箱做全局变量查找缓存，性能有所优化； 支持 vite 运行，但必须使用 plugin 改造子应用，且 js 代码没办法做沙箱隔离； 对于不支持 webcompnent 的浏览器没有做降级处理；
